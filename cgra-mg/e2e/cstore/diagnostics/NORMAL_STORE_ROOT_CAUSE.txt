## Root cause and ownership

The production defect is in `VitraCGRAController.scala`:

```scala
class TileStateCtrl(numIOB: Int, numTiles: Int) extends Module {
  ...
  val exeTileEnReq = Input(UInt(numIOB.W))
  ...
  val exeRelatedTileReg = RegInit(0.U(numIOB.W))
  ...
  tileState.io.exeTileEnReq := exe_en_tiles
}
```

This generated CGRA has `numIOB=6` per tile and `numTiles=8`. The full 8-bit
selected-tile mask is therefore truncated to 6 bits. The failing normal case uses
tile mask `0x94` (tiles 7, 4, 2), which becomes `0x14`; tile 7 is omitted from the
completion dependency. TileStateCtrl consequently considers the related set done,
leaves `s_exe_run`, and deasserts `cgra.io.en` while tile-7 IOB 484 is still in its
latency state. The control target is on tile 5, which remains representable in six
bits and stays enabled through its issue cycle.

This directly satisfies the VITRA ownership condition: the ADORA config delivers
the correct lane-0 value and correct schedule, but VITRA disables the configured
pipeline before the value can be consumed. Therefore:

```text
OWNER = VITRA
```

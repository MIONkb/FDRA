== Current SRAM cycle path

The complete current STORE ingress/request path is:

[source,text]
----
IOB routed inputs
  -> one Muxn per operand
  -> two-lane SharedDelayPipe
  -> IOController io.in(0=data, 1=byte address)
  -> wData / selected affine-or-routed addr / wValid / realEn
  -> optional SRAM request registers selected by addRegSram
  -> sram.en / sram.we / sram.addr / sram.din
----

`IOB` connects the mux outputs to `SharedDelayPipe`, then its two outputs to `IOController`; the controller's SRAM interface is connected back through the IOB to the VITRA scratchpad banks.
The SRAM_MODE IOB controller decodes `BaseAddr`, nested `Stride`/`Cycles`, `II`, `Latency`, `IsStore`, and `UseAddr` from its configuration word.
`start` moves the controller through `s_idle`, optionally `s_pre_lat`, and then `s_data`; the II and nested cycle counters qualify store data or a load address.

For a store, `io.in(0)` supplies data and either the generated address or `io.in(1)` supplies the byte address when `UseAddr` is set.
For a load, the generated address or `io.in(0)` supplies the byte address when `UseAddr` is set; SRAM `dout` returns through `io.out(0)`.
`realEn` qualifies the SRAM request, while `IsStore` selects a nonzero write enable.

The supported `addRegSram` latency contract is:

[cols="1,1,1,3",options="header"]
|===
|`addRegSram` |Store latency |Load latency |RTL staging

|0
|0
|1
|Combinational request path; SRAM response goes directly to `io.out(0)`.

|1
|1
|2
|Request enable, write enable, address, and store data are registered.

|2
|1
|3
|The request is registered and the load response receives one additional register.
|===

The architecture metadata computes `load_latency = addRegSram + 1` and `store_latency = 0` only for `addRegSram == 0`, otherwise 1.

== COND_LS_MODE audit

`VitraTask1AuditSpec` shallow-clones `VitraSpec.attrs`, installs replacement IOB-spec rows whose modes are `COND_LS_MODE`, disables ADG and operation-set dumps, elaborates `MultiTileCGRA`, and restores the global map in `finally`.

The present parameter, IOB, controller, generator, and artifact discontinuities are:

* `IobParam` assigns three operand groups to COND_LS_MODE: data, address, and enable/predicate.
* `IOB.numInCtrl` assigns only two controller inputs to every non-FIFO mode. Both the mux instance-ID list and emitted ADG `num_operands` are derived from that two-input count.
* `IOB.numDelayPipes` creates only two delay-pipe lanes for every non-FIFO mode.
* `IOController.numIn` exposes only two inputs for every non-FIFO mode.
* `IOController` configuration contains `IsStore` and `UseAddr` but no `UseEn`; `wValid`, `realEn`, and the final `sram.we` path do not consume a runtime predicate.
* The conditional operation-list skeleton advertises `CINPUT`, `COUTPUT`, `CLOAD`, and `CSTORE`, even though elaboration fails before a matching three-operand IOB/ADG can be emitted. In particular this is not evidence that CLOAD works.
* Production `VitraSpec` remains `SRAM_MODE`. Checked-in metadata remains mode 1 with two-operand IOBs; checked-in operations contain only `INPUT`, `OUTPUT`, `LOAD`, and `STORE`, with no CSTORE capability.

Elaboration therefore reaches the third COND_LS operand while the `Muxn` instance-ID list contains only two entries.
The observed exception is `java.lang.IndexOutOfBoundsException: 2`.
The real first user-code frame from the focused run is:

Predicate representation is *TO VERIFY*: the current structure suggests a third operand group, but Task 1 does not establish whether the predicate is a one-bit Boolean, a data-width lane, or another encoded control representation.
Until the controller lane and representation are specified and implemented in later work, conditional operations including `CLOAD` remain unsupported.
